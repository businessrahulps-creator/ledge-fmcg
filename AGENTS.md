- Signed-in pages render inside one persistent AppShell layout route (App.tsx); page-level <AppLayout> is a pass-through there — why: sidebar/header must not rebuild on every page switch.
- Today's work rules live as pure functions in src/lib/intelligence.ts (no AI for numbers); handled cards persist in intel_actions, thresholds in companies.intel_settings — why: testable, trustworthy, no nagging.
- Dealer credit days are current-term metadata in credit-terms.ts/receivables.ts for internal collections only, calculated after existing allocations; never alter or block invoices, billing, orders, prices, tax or payment calculations — why: collection tracking must not change financial documents or money behaviour.
- Buying (suppliers, purchase bills, returns, supplier payments) lives in its own tables; every write goes through SECURITY DEFINER `*_atomic` RPCs, and supplier balance = opening + posted bills − returns − posted payments (`supplier_balance` SQL, mirrored in src/lib/payables.ts). Why: same immutable, all-or-nothing rules as sales bills.
- Shop visits (CRM) lives in shop_visits + shop_prospects with company-scoped RLS; converting a new shop to a dealer goes through `convert_prospect_to_dealer_atomic`, and a promise to pay writes an intel_actions "promised" row so Today's work brings the dealer back on the promised day. Why: one dealer record, no duplicate customer table, reuse Today's work rules.
- Buying access uses its own `manage_buying` capability (default owner + accountant), checked in buying RPCs, RLS and UI — why: buying is separate from seeing sales money.
- Orders are sent only via `dispatch_and_bill_order_atomic`; the old `dispatch_order_atomic` is revoked from clients — why: it skipped stock and credit checks.
- Menu items, order and names come from `src/components/layout/nav-config.ts`, shared by the computer sidebar, phone bottom bar and phone Menu, with Dashboard always first — why: the two menus drifted when built separately.
- Page titles use `.h1-display` via PageHeader; small buttons get `touch-target` (44px touch); dialogs open ≤200ms ease-out, no slide — why: one spacing/motion system.
- No undo-send after a GST bill. Why: bills change only via credit notes.
- Overpay/cancel-with-advance need owner choice; extras = child invoice_payments, refund_due/refunded status; money RPCs lock per company. Why: no guesses/races.
- Deleting an order goes only through `delete_order_atomic`; stock_deductions has no client write access, and triggers keep dealer balances/totals and product total_sold/avg_cost server-owned (credit-limit changes need override_credit_limit or manage_team) — why: direct writes let non-owners restore stock or lift credit limits.
- CSV exports prefix = + - @ with '; Tally XML strips control chars — why: injection, bad XML.
- Startup data loads order_lines/order_schemes/claim_lines embedded in their parent select (no follow-up id-list requests), and permissions load once via `my_capabilities` — why: the second request wave and duplicate permission calls were most of the open-time.
- Activity history is written by the database (`tg_audit_row` trigger on business tables, same transaction, before/after for edits); the app only records refused saves via `log_failed_attempt`, and bell alerts fan out from activity_log by capability — why: client-side logging could be skipped or forged and missed money events.
- Every activity_log row also lands in the bell: `tg_activity_notify` writes `priority='important'` alerts (others, by capability, count in the badge) and a quiet `priority='normal'` copy for money-access users incl. the actor, bundled per type+action+person+IST day and inserted already read; the bell loads important rows separately — why: owners see everything without the badge flooding.
- Computer account menu (Settings + Sign out) lives in the top bar via ProfileMenu; role picture has one home in RoleAvatar.tsx (each role has its own lazy-loaded calm bot: owner square, manager circle, accountant triangle, salesperson drop, viewer sleeping pebble; coloured initial is the loading fallback) — why: one way into Settings, consistent role styling.
- Per-person access = role defaults + user_capability_overrides for the toggleable areas (server list _access_toggleable()); written only via set_member_access_atomic or invite acceptance (team_invites.capability_overrides); job changes only via change_member_role_atomic (clears custom access; owners cannot be changed or removed); clients have no direct write access to user_roles, user_capability_overrides or team_invites inserts; Company page gated by manage_business — why: owner-controlled, server-checked, one source of truth.
- Orders and order lines may only link to the same business's dealers, salespeople, godowns and products (DB triggers), and app users can't set payment_status directly — why: RLS checked only company_id, so foreign links and forged paid status got through.
- New orders save via the 9-arg `book_order_atomic` with a per-attempt save ID (orders.idempotency_key); money RPCs lock order before bill — why: no duplicate orders, no deadlocks.
- /welcome never shows while `my_pending_invite()` finds a matching invite (NoCompanyGuard + Welcome redirect to it; sign-up and email-confirm keep the invite redirect) — why: invitees were making empty businesses.
- OrderDetail's GST-rate gate uses the tested pendingOrderGstProducts rule matching dispatch_and_bill_order_atomic — why: no-GST bills must not be blocked by product tax settings.
- Dealer attribution: acquired_by/acquisition_date are set only by server functions (clients can't write them); assigned_salesperson_id needs see_all_dealers or manage_team; salesperson links must be same-business (triggers in 0070) — why: acquisition credit is historical and must not be forged; revenue stays on orders.salesperson_id.
- Dashboard financial sections and AI explanations require server-backed see_money; setup requires manage_business, and greetings use Asia/Kolkata — why: shared home screens must respect access and the business clock.
- Salesperson detail financial summaries, payment-derived indicators, revenue target progress and statement downloads require see_money; non-money target progress uses order counts only — why: derived percentages and exports must not reveal hidden financial results.
- Targets financial inputs, summaries and revenue-derived status require see_money; manage_schemes still controls editing, and non-money order-target saves retain existing revenue goals — why: hiding financial fields must not disclose or overwrite them.
- Dealer Detail financial panels, payment-derived indicators, order amounts, statement PDF and financial WhatsApp share require see_money; unauthorized ledger tab URLs fall back to overview — why: direct links and exports must follow the same screen access rule.
- Stock valuations use canViewStockValue (manage_stock OR see_money) across godown cards, summary, inventory table and inventory export; product prices and quantities are unchanged — why: the same aggregate must not leak through another stock view.
- Returns bill selection uses isReturnableBill for order-linked issued gst_invoice documents (final/posted/partial/paid; intra_state/inter_state/bill_of_supply), excluding drafts and unknown/cancelled statuses — why: BOS is a supply type and payment status does not revoke an issued bill; return calculations and server checks remain unchanged.
